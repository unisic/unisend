# Parity with Beeper

Target: what Beeper Desktop 4.3.308 and Beeper Android 4.64.0 do, on GPUI
instead of Electron. The feature list below comes from the shipped apps (UI
strings, hotkey table, Matrix event types in the desktop bundle); the protocol
notes say how each feature is stored so that changes sync with Beeper's own
clients. Nothing from those apps is copied into this repo.

Status: `done` works and is tested, `part` works with the gaps named, `todo`
is not started.

## Account and sync

| Feature | Status | Protocol |
|---|---|---|
| Email-code login | done | `api.beeper.com/user/login*`, then `org.matrix.login.jwt` |
| Other Matrix homeservers (not in Beeper) | part | `.well-known/matrix/client` discovery, then `GET /_matrix/client/v1/auth_metadata` and `GET /login`. OAuth 2.0 (MSC3861, Matrix Authentication Service as on matrix.org) when the server has it: dynamic client registration, PKCE, refresh tokens written back to `session.json`; else `m.login.sso` (one button per identity provider) and `m.login.password`. The page opens in the system browser on desktop and comes back to `http://127.0.0.1:<port>/`, a listener that takes one answer and closes (10 min at most); on Android it opens in the app's own browser (WebLogin), which stops at that address without loading it. https only (http for localhost). Not yet: registration, QR login. Networks are left out of the navigation there: bridges and the account API are Beeper's |
| Encrypted history via recovery code | done | secret storage, key backup v1 |
| Device verification by another device (QR, emoji) | todo | `m.key.verification.*` |
| Chat networks: list, sign in, sign out | part | cloud bridges only: `api.beeper.com/whoami`, `POST /bridge/{name}/start`, then the bridge's mautrix provisioning API (`/v3/whoami`, `login/flows`, `login/start`, `login/step`, `logout`) proxied at `matrix.beeper.com/_matrix/client/unstable/com.beeper.bridge/{name}/`. Steps: form fields, QR or code, browser cookies (in-app browser on Android and Linux, paste on Windows and macOS, and on Linux when its browser cannot open). Not yet: cookie sources other than cookies, re-login of a broken account, Beeper's browser-session import |
| On-device bridges | todo | Beeper runs local mautrix bridges inside the client |
| Multiple accounts, account filter, spaces bar | part | up to three accounts side by side, each with its own backend, switched in Settings (`src/accounts.rs`). A shared inbox, opt-in per account on this device (`Settings::shared_inbox`), lists their chats together, each marked with its account's picture; opening one turns the window to its account. Todo: spaces bar (`m.space`), Beeper's chat list rules (`com.beeper.chat_list_rules`) |
| Connection state (offline, syncing, reconnect) | part | one quiet line while the connection is lost and retried (5 s doubling to 60 s); no syncing indicator |

Merge from the chat's sheet or from a proposal over the composer: one-to-one chats with the same `tel:` number or full name (Beeper also matches email and Beeper contacts, which this list does not have). Split from the sheet: one chat out (`{}`), or all (leave and forget the union room); deleting a chat takes it out too, and the last one out ends the union. | Swipe actions | done | a chat row swiped either way runs the action chosen in Settings (default: left archives, right marks read or unread; delete asks first); local setting |
| New chat, new group, contacts | done | + in the chat list: Beeper/Matrix (user directory, a Matrix ID on any server typed or pasted as a matrix.to link or `matrix:u/` URI, also when adding to a group; an existing DM is reused) or a network login, then a contact, a search result or a typed phone number or username. bridgev2 provisioning `GET capabilities`, `GET contacts`, `POST search_users`, `GET resolve_identifier/{id}`, `POST create_dm/{id}`, `POST create_group/{type}` (name and members as the network's capabilities allow); Matrix `createRoom` (private, encrypted). Other bridged chats are only left here: bridgev2 drops Matrix leaves unless `bridge_matrix_leave` |

## How Beeper stores chat state

- Archive: room account data `com.beeper.inbox.done`. Archived means
  `at_order >=` the `com.beeper.hs.order` (event `unsigned`) of the newest
  message that counts as unread; without `at_order`, `updated_ts >=` the last
  activity and the chat is read. Pinned chats are never archived. Unarchive
  writes `{}`. Archiving marks the chat read unless
  `com.beeper.mark_read_when_archive` is `{enabled: false}` (Desktop also
  gates that setting on a feature flag, which this client does not read).
- Pin: tag `m.favourite` (order 1). Low priority: tag `m.lowpriority` (order 0).
- Mute: a push rule of kind `room` (id: the room id) whose actions do not notify (`[]` or `["dont_notify"]`), matrix-sdk's `MentionsAndKeywordsOnly`. Checked read-only on a live Beeper account: every mute there was such a rule, none an override rule.
- Marked unread: `m.marked_unread` `{unread}`.
